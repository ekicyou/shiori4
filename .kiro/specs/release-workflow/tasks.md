# Implementation Plan

- [ ] 1. リリース CI の補助スクリプト
- [x] 1.1 (P) タグの検査スクリプトを作る
  - タグの形（`vX.Y.Z`、ASCII 数字だけ）・タグのコミットのワークスペースの版との一致・main からの到達・見どころのファイルの中身の 4 条件を、すべて確かめてからまとめて報告する
  - 合格なら版を出力に書き、不合格なら失敗した条件の箇条書きと「どの公開先にも公開していない」を summary に書いて失敗で終わる
  - 手元（`GITHUB_OUTPUT` が無い環境）では結果を標準出力へ書く
  - 完了の状態: `-Tag v0.0.1 -Sha (git rev-parse origin/main) -MainRef origin/main` で実行すると、形・版・到達が合格し、見どころだけが不合格で終わる（v0.0.1.md はまだ無い）。`-Sha HEAD` では到達も不合格になる（統合前の作業ブランチのため）
  - _Boundary: verify-tag.ps1_
  - _Requirements: 1.3, 1.4_

- [x] 1.2 (P) 詳しいリリースノートと Release の本文を作るスクリプトを作る
  - 1 つ前のリリースタグ（無ければ履歴の先頭）から範囲の終わりまでのコミットを、件名の種類で 7 つの見出しに分け、内部の作業（種類 `spec`・決まったスコープ・`kiro-` で始まるスコープ・`chore(release)`）とマージコミットを載せない
  - 1 行目に製品名・版・件数を持つ見出しを置き、前のタグがあるときだけ末尾に compare のリンクを置く。タグがまだ無い版（範囲の終わりの指定）でも同じ形を出す
  - 本文のファイルは、見どころ（改行を LF に、末尾の空白と改行を落とす）＋区切り＋詳しいリリースノートの全文にする。失敗したときはどのファイルも残さない
  - 完了の状態: 今のリポジトリで範囲の終わりを `HEAD` にして実行すると、全履歴の変更が分類され、`Full Changelog` の行の無いノートが出る
  - _Boundary: release-notes.ps1_
  - _Requirements: 4.3, 4.4, 4.5, 6.5, 6.6, 6.7_

- [x] 1.3 (P) 1 クレートを冪等に公開するスクリプトを作る
  - crates.io の API でクレートの有無と版の有無を確かめ、未登録は `not-registered`、公開済みは `skipped`、200・404 以外は `transient` として status 契約の行を書く
  - 下位のクレートの同じ版が索引に現れるのを上限つきで待ち、`--locked`・`--no-verify` を付けずに公開し、依存の未解決は回数を限って再試行する。401・403 は `auth`、ほかの失敗は `publish` にする
  - 公開した版が API に現れるのを上限つきで待ち、現れなければ `transient` にする。所要時間と次の手を summary の行に書く。yank・上書きをしない
  - 判定だけを行い、公開せずに行うはずの操作を表示する dry-run を持つ
  - 完了の状態: 手元で `shiori4_abi` の `0.0.1` を dry-run すると、`failed`・`not-registered` の status の行が出る（公開前の今の状態）

  - _Requirements: 3.1, 3.4, 3.5, 3.6, 3.7, 3.8, 3.10, 3.11_

- [ ] 2. リリース CI のワークフロー
- [ ] 2.1 タグの検査・関門・crates.io への公開の job を組む
  - リリースタグの形の push だけで起動し、同じタグの実行を取り消さずに直列にする。トップの権限は読み取りだけ
  - verify の job がタグの検査スクリプトを呼んで版を出し、gate の job が PR の CI（build.yml）をそのまま呼ぶ

  - 集約の step が、設計の 4 つの規則でクレートごとの status・reason を決めて job の出力にし、次の手の表を summary に書く
  - 完了の状態: ワークフローのファイルが YAML として読め、job の needs・権限・step の id と名前が設計の表と一致する（actionlint を使えれば通す）
  - _Depends: 1.1, 1.3_
  - _Requirements: 1.1, 1.2, 1.4, 1.5, 2.1, 2.2, 3.1, 3.2, 3.3, 3.9, 3.11, 5.4_

- [ ] 2.2 GitHub Release と報告の job を組む

  - report の job は、どの段で止まっても走り、4 つの公開先の status・reason と Release の URL（無ければ「なし」）を 1 枚の表にし、走らなかった段だけを `not-run` にし、ほかは推測せず summary を参照させる
  - 公開前の段で止まったときは、止まった job と「どの公開先にも公開していない」を表の前に書く。report 自体は成功で終わる
  - 完了の状態: ワークフローの 5 つの job（verify・gate・publish-crates・github-release・report）がそろい、書き込みの権限が github-release にだけある
