# 別のプロセスの注意

SHIORI を専用のプロセスで読むベースウェアの作者に向けて、別のプロセスにしたときに起きる止まり方と時点のずれを 3 つの注意にまとめる。教科書の目次は [doc/textbook/README.md](https://github.com/ekicyou/shiori4/blob/main/doc/textbook/README.md) にある。

## この章の読み方

- 規約の正本は C ヘッダ [`shiori4_abi/include/shiori4_abi.h`](https://github.com/ekicyou/shiori4/blob/main/shiori4_abi/include/shiori4_abi.h) の冒頭の注釈と、`shiori4_abi` のクレート冒頭の `//!` である。この章は正本を言い直したもので、食い違ったら正本が正しい。
- 「スレッド規約 2」「戻り値 2」「ホストのプロセス 1」などの引き方は、[規約の一覧](https://github.com/ekicyou/shiori4/blob/main/doc/textbook/rules.md)の「番号の付け方と引用の仕方」に従う。各規約の理由も規約の一覧にある。
- ホストは SHIORI を専用のプロセスで読むことがある（ホストのプロセス 1）。たとえば areka は、SHIORI ごとに helper のプロセスを起こし、その中で `shiori4_host` を使う（規約の一覧の「ホストのプロセス 1」の理由）。この章では、SHIORI を読んで ABI で呼ぶ側のプロセスを「子」、ベースウェアの本体のプロセスを「親」と呼ぶ。また、子のホストが SHIORI からの `host.request` と `host.post` を親へ中継するものとして述べる（この章の想定で、規約ではない）。
- ABI の形は、同じプロセスで読むときと変わらない（規約の一覧の「ホストのプロセス 1」の理由）。変わるのは、親と子の間の往復と待ち方である。

## 注意 1: 同期の往復で互いに待って止まる

- SHIORI が `host.request` を呼べるのは、`load`・`request`・`notify` を呼ばれているスレッドから、その呼び出しが返るまでの間だけである（スレッド規約 2）。呼ばれた側は `out` を最後に書き（ABI 規約 6）、SHIORI は応答を受け取ってから自分の処理を続ける。
- 子のホストが `host.request` を親へ中継すると、IPC の往復になる（ホストのプロセス 2）。この往復は同期で、SHIORI は親の答えが戻るまで、`load`・`request`・`notify` の途中で待っている。
- そのため、親が子へ `request` を送って SHIORI の応答を待っている間に、その SHIORI の `host.request` が子から親へ届くことがある。親が SHIORI の応答だけを待つ待ち方をしていると、親は SHIORI の応答を、SHIORI は親の答えを待って、互いに待って止まる。
- 親は、SHIORI の応答を待つ間にも、子からの問い合わせを受けて答えられる待ち方にする。答える処理の中で、ホストから SHIORI を呼び返してはならない（スレッド規約 3。違反は `SHIORI_E_REENTRANT`）。
- 同じプロセスの中でも、UI スレッドが `request` の応答を待つ間に SHIORI がワーカースレッドから `host.request` を呼ぶと、その問い合わせに UI スレッドで答えようとするホストは同じように止まる（規約の一覧の「スレッド規約 2」の理由）。スレッド規約 2 は、この呼び方を許さない。
- SHIORI の作者は、`host.request` が IPC を往復して遅くなりうることを前提にする（ホストのプロセス 2）。

## 注意 2: post の受付と完了は別の時点になる

- `host.post` は任意のスレッドから呼べる。ホストは msg をコピーしてすぐ返り、post はキューに積む（スレッド規約 4）。この章の想定では、子のホストは post を受けてキューに積み、親へ送る。
- post の戻り値は受付の可否だけである（204: 受付、400: 不正、`SHIORI_E_SHUTDOWN`: 終了中。post の完了通知 2）。204 は受け付けたことを伝えるだけで、親での処理が終わったことは伝えない。
- 完了は、ホストが通常のイベント（request または notify）として、post したインスタンスに届ける（post の完了通知 3）。post の呼び出し中や `host.request` の処理中には届けず、イベントループから届ける（同じ所）。完了の中身は `ID: OnHostComplete` のイベントである（[`doc/host-protocol.md`](https://github.com/ekicyou/shiori4/blob/main/doc/host-protocol.md) 第 6 章）。
- そのため SHIORI は、受付 ID を発行して登録してから post する（post の完了通知 1）。登録より先に post すると、完了が先に届いたときに文脈が見つからない（規約の一覧の「post の完了通知 1」の理由）。
- 結果が要らない post には `Tag` を付けない（post の完了通知 4）。
- unload を始めたら、そのインスタンス宛ての未配送イベントは破棄する（post の完了通知 3）。受け付けた post の完了が、必ず届くとは限らない。

## 注意 3: PANIC と子の異常終了はインスタンスの終わり

- エクスポートする関数は、例外・パニックを境界の外へ出さず `SHIORI_E_PANIC` を返す（ABI 規約 8）。`SHIORI_E_PANIC` が返ったら、ホストはインスタンスを unload する（戻り値 2）。親は、そのインスタンスを終わったものとして扱い、そのインスタンスへ要求を送り続けない。
- 子のプロセスが異常終了したときも、この章ではインスタンスの終わりとして扱う。インスタンスは子のプロセスの中にあったので、子が終わればインスタンスも残らず、unload を呼ぶ相手もいない。
- unload を始めたら、そのインスタンス宛ての未配送イベントは破棄する（post の完了通知 3）。子が異常終了したときは、完了を届ける先のインスタンスがもう無い。
