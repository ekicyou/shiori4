# リリースノートの見どころ

このフォルダには、版ごとの見どころのファイル `vX.Y.Z.md`（`X.Y.Z` はその版）を置く。この文書が、見どころの書き方と、内部の作業の決まりの正である。

## このフォルダの役割

- `vX.Y.Z.md` の中身は、リリース CI がそのまま GitHub Release の本文の先頭に置く。末尾の空白を落とし、改行を LF にそろえるほかは、書き換えない。
- リリース CI は、本文の見どころの後に、区切りの線（`---`）と、詳しいリリースノートの全文（版と載せた変更の件数が見出しに入る）を足す。見どころのファイルには、版・件数・詳しいリリースノートへのリンクを書かない。
- タグが指すコミットに、タグの版の見どころのファイルが無いとき、または中身が空白と改行だけのとき、リリース CI はタグの検査で失敗し、どこにも公開せずに止まる。
- 見どころのファイルは、`release` スキルの段 4（版の更新）で書き、版の表記の更新と同じコミットに入れる。

## 書き方

1. 日本語の Markdown で書く。GitHub のリリースの本文として、そのまま表示される。
2. 見どころは 3〜5 件。直しだけの版は 1〜2 件でよい。
3. 見どころごとに `###` の見出しを 1 つ付け、末尾に元になった PR の番号を `(#83)` の形で付ける。複数は `(#63, #77)`。PR を通らなかった変更には付けない。
4. 動きが変わる点（破壊的変更）は、すべて載せる。1 つの見出しの下に、普通の文体の箇条書きで書き、各項目の末尾に PR の番号を付ける。
5. spec 名（`.kiro/specs/` のフォルダの名前）と、`feat(…):` のような接頭辞を書かない。

語り手や口調の決まりは持たない。

### 形の見本

文面は例である。

```markdown
## 今回の見どころ

### 起動の時間を半分にした (#83)

起動のときに読む設定を、使う時点まで読まないようにした。

### 動きが変わる点が 2 つ

- 設定のファイルが無いときは、既定の値で動く。 (#70)
- 空の応答では、改行を出さない。 (#69)
```

## 次の版の印

版は `/release` の段 4 まで決まらない。まだ出ていない版を指す文書（教科書・spec・README・コードの注釈など）には、版の番号を予想して書かず、印 `X.Y.Z-next` を書く。タグやリンクでは `vX.Y.Z-next` と書く。

```markdown
- **当てはまる版**: shiori4 X.Y.Z-next から。
- [`vX.Y.Z-next` のタグ](https://github.com/ekicyou/shiori4/tree/vX.Y.Z-next)
```

`/release` の段 4 が、リポジトリの中の印を、リリースする版（例: `0.1.0`）に置き換えて、版の更新と同じコミットに入れる。印を説明している `.claude/skills/release/` とこのフォルダは、置き換えの対象から外す。出た版の番号は、そのまま番号で書いてよい。

## 内部の作業

詳しいリリースノートに載せない変更の決まりである。コミットの件名の種類とスコープに、上から当て、どれかに当てはまれば載せない。マージコミットは、件名にかかわらず載せない。

| # | 条件 | 例 |
|---|------|----|
| 1 | 種類が `spec` | `spec(discovery): …` |
| 2 | スコープが `spec`・`discovery`・`roadmap`・`steering`・`skills`・`cc-sdd`・`release-workflow`・`kiro` のどれか、または `kiro-` で始まる（種類は問わない） | `docs(roadmap): …`・`chore(kiro-skills): …` |
| 3 | 種類が `chore` で、スコープが `release` | `chore(release): v0.0.2` |

種類とスコープは、大文字と小文字を区別しない。spec 名をスコープにしたコミット（例: `feat(crate-publish-ready): …`）は、`release-workflow` のほかは載せる。

決まりを当てる場所は `.github/scripts/release/release-notes.ps1` である。決まりを変えるときは、このスクリプトの定数（`$InternalScopes` と `Test-Internal`）と、この表を合わせて直す。

## 材料の出し方

どちらも、リポジトリのルートを作業ディレクトリにして、PowerShell で 1 行で動かす。`{V}` はリリースする版（例: `0.0.2`）である。

材料の一覧（1 つ前のリリースタグから main の先頭までの変更を、詳しいリリースノートと同じ形で出す。タグを打つ前でも動く）:

```powershell
& "$PWD/.github/scripts/release/release-notes.ps1" -Tag v{V} -Repo ekicyou/shiori4 -Head origin/main
```

出力の最後の行は `**Full Changelog**: https://github.com/ekicyou/shiori4/compare/v{前の版}...v{V}` になる。違うときは、前のタグを読めていない。

初版（0.0.1）のように 1 つ前のリリースタグが無いときは、履歴の先頭からのすべての変更が材料になり、`**Full Changelog**` の行は出ない。

見どころのファイルの確認（4 行の `合格`／`不合格` を出す。読むだけで、何も変えない）:

```powershell
& "$PWD/.claude/skills/release/scripts/highlights-check.ps1" -Version {V} -Head origin/main
```

4 行（見どころのファイル・PR の番号・動きが変わる点・spec 名）が、すべて `合格` になるまで直す。
