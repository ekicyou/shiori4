# release — shiori4 のリリース

このスキルを実行するたびに、下の段を 1 から順に行い、実際のリリース（版の更新・PR・リリースタグの push・リリース CI の見届け）を行う。検査と公開（crates.io の 3 クレート `shiori4_abi`・`shiori4`・`shiori4_host` と GitHub Release）はリリース CI（`.github/workflows/release.yml`）が行う。見どころのファイル（`doc/release-notes/vX.Y.Z.md`）は、段 4 でこのスキルが書く。詳しいリリースノートの生成と、リリースの本文の組み立ては、リリース CI が行う。

段 1〜9 が実行するコマンド・合否の基準・判定表は、同じフォルダの [procedure.md](procedure.md) にだけ置く。下の「段 N」は、procedure.md の同じ番号の段の節を指す。procedure.md の見出しを指すときは、かぎかっこの前に「節」を付ける。段の中の太字の小見出しを指すときは、かぎかっこの前に「段 N の」を付ける。

要件と設計は `.kiro/specs/completed/release-workflow/` にある。かっこの中の番号（7.7 など）は、その要件の番号である。実行には使わない。

## 実行の約束

1. 段はメインの文脈で、番号の順に 1 つずつ行う。サブエージェントへ任せない（開発者への確認があり、値を次の段へ渡すため）。レビュー・デバッグのサブエージェントを使わない。失敗は判定表で扱う。
2. テストを書かない。段の完了は、段が定める確認のコマンドの結果で判定する。
3. コミットしてよいのは、段 4 の版の更新の 2 ファイル（`Cargo.toml` と、見どころのファイル `doc/release-notes/v{V}.md`）だけである（7.8）。`git add` には必ずファイルのパスを並べる（`git add -A`・`git add .` を使わない）。
4. 進み具合をファイルに書かない（7.8）。実行変数もファイルに書かない。再開の位置は、前回の実行の記録でなく、段 2 の判定表で決める。
5. main へ直接 push しない。push するのは、作業ブランチ（PR のため）とリリースタグだけである。
6. 手元で `cargo build`・`cargo test` を実行しない。段 4 でも `cargo` のコマンドを実行しない（`Cargo.lock` はコミットしない）。main の CI の結果を見ない（7.7）。
7. 手元から `cargo publish`・`gh release create`・`gh release upload` を実行しない。公開済みのものに `cargo yank`・`gh release delete` を実行しない（7.7）。公開前の検査はリリース CI に任せる。
8. 判定表・手順に無い状態に当たったら、推測で進めず、「止まり方」に従って止まる。
9. 版の指定は、`0.0.2` か `v0.0.2` の形（数字 3 つ）で受け取る。
10. コマンドは、1 回のツールの呼び出しに 1 行ずつ実行する。`procedure.md` の 1 つのブロックに複数の行が並んでいても、1 行ずつ分けて実行する。複数の行を `;`・`&&` でつながない。終了コードを見るための `echo` などを足さない。つなぐと許可の規則（`Bash(gh pr merge:*)` など）に合わなくなり、許可の判定に拒否される。`procedure.md` がパイプを含めて 1 行に書いている行と、`powershell` のブロックの複数行にわたる 1 つの文（`foreach` など）は、そのまま 1 回で実行する。許可の判定に拒否されたら、言い直して実行し直さず、「止まり方」に従って止まる。

`bash` のブロックは Bash ツールで、`powershell` のブロックと定型コマンドは PowerShell ツールで実行する。

### 止まり方

「止まる」は、残りの段を行わず、次の形の報告を出して終えることである（13.3）。

```
リリース未完了: v{V}（止まった段: 段 N・理由）
- 公開済みの公開先: <定型コマンド A の「あり」の行。無ければ「なし」>
- 残っている公開先: <公開先と status・reason。無ければ「なし」>
- 原因の区分: <判定表の行の名前>
- 公開前の段で止めた場合: どの公開先にも公開していない（定型コマンド A で 0/4 を確かめてから書く）
- 次に誰が何をするか: <開発者 / エージェント と、その内容>
- 再開の方法: /release をもう 1 度実行する（状態から続きを判定する）
- 手順との食い違い: <なし / 手順どおりに動かなかった箇所>
```

版が決まる前（段 1〜3）に止まるときは、1 行目を「リリースを開始できない（止まった段: 段 N・理由）」とし、何も公開していないことを書く。

## 段の進め方

1. 毎回、段 1 から始める。
2. 段 N を始める前に、`procedure.md` の「段 N」を読み直す。コマンドは、`procedure.md` に書いてあるものを、波かっこ（`{V}` など）だけ置き換えて実行する。記憶で書かない。足さない。
3. 定型コマンド A・B・C・D は、節「定型コマンドの呼び出し方」の 1 行で呼ぶ。スクリプトの中身を写して実行しない。出力の読み方は、節「定型コマンド A の出力（状態の照会）」と節「定型コマンド B の出力（リリース CI の結果）」にある。
4. 判定の結果、行わないと決まった段は、行わずに次へ進む（下の各段の「飛ばす」）。
5. 段を終えるたびに、確定した実行変数（節「実行変数」の `VREQ`・`V_MAIN`・`V`・`BRANCH`・`PR`・`TARGET`・`RUN`・`ATTEMPT`・`N_AUTO`・`F7_DONE`）を開発者に 1 行で示す。`N_AUTO` は 0、`F7_DONE` は「いいえ」から始める。
6. すべての段は直列である。並行に行える段は無い。

## 段

### 段 1. 開始の確認を行う

節「段 1: 開始の確認」に従う。

- 最初に `VREQ` を決める。開発者の指示（スキルの引数）に版の指定があれば、先頭の `v` を外したものを `VREQ` とする。無ければ `VREQ` は無しとする。`VREQ` が数字 3 つの形でなければ（段 3 の手順 3 のコマンドで確かめる）、エラーを示し、入力し直しを求める。
- 手順 1（ブランチ）と手順 2（必要な操作）は、何も変えない。どちらかが不合格なら、何も変えずに止まる。
- 手順 3 で、未コミットの変更か main に無い内容があれば、内容を示して止まり、main の先頭から作った新しい作業ブランチでの実行し直しを求める。
- 手順 3 の「版の更新のコミットだけが残っている場合」（コミットが 1 つで、変更が 2 ファイルだけ）にあたるときは、止まらずに手順 3 の「続け方」に従う（以下「統合からの再開」と呼ぶ）。コミットの件名の版を `V` として開発者に示す。`VREQ` があって `V` と違うときは止まる。手順 4 の後、段 2 を飛ばし、「続け方」の 3 つの確認を行い、段 5 から続ける。
- 手順 4 で、main を履歴を書き換えずに取り込む。衝突したら取り込みを中止して止まる。
- 完了の状態: `VREQ` と `BRANCH` が決まり、手順 2 の 4 つのコマンドが合格し、権限の出力が合格の 3 つのどれかであり、手順 3 が合格し（または「統合からの再開」に入り）、`git merge-base --is-ancestor origin/main HEAD` が終了コード 0 である。

### 段 2. 実際の状態から、始める位置を判定する

節「段 2: 状態の判定」に従う。

- 定型コマンド A を版の指定なしで実行し、出力を判定表 S0〜S9（S2 は欠番）に上から当て、最初に当てはまった行に従う。`main` の行の版を `V_MAIN` とする。
- 前回の実行の会話の記録を、判定に使わない。
- 止まる行（S0・S6・S8・S9）: 判定表の「次の手」の内容を示し、「止まり方」で止まる。
- 開発者の答えを待つ行（S1）: エラーを示して別の版の入力を求め、入力されたら段 3 を手順 3 から行う。
- 進む行（S3・S4・S5・S7）: S3 は段 3 へ進む。S7 は段 3〜5 を飛ばし、段 6 へ進む。S4 は段 3〜6 を飛ばし、段 7 を手順 2 から行う。S5 は段 3〜6 を飛ばし、段 7 を手順 3 から行う。S4・S5 で `VREQ` が `V_MAIN` と違うときは、`V_MAIN` のリリースが未完了なので先に続きを行うことと、`VREQ` は始めていないことを開発者に示す。
- 段 3 を飛ばす行（S4・S5・S7）では、`V` を `V_MAIN` とし、開発者に示す。段 6 も飛ばす行（S4・S5）では、`RUN` と `ATTEMPT` を、定型コマンド A の `run` の行の ID と `attempt` から取る。
- 飛ばす: 段 1 が「統合からの再開」に入ったとき。
- 完了の状態: 当てはまった行の番号（S0〜S9）、`V_MAIN`、次に行う段の番号を、定型コマンド A の出力の該当の行とともに開発者に示してある。

### 段 3. リリースする版を決める

節「段 3: 版の決定」に従う。

- 手順 1〜5 を順に行う。版の指定が無いときは、定型コマンド A の `提案` の行の版（最大の版の PATCH + 1）を候補にし、出どころごとの最大の版とともに開発者に示す。承認を求めない。答えを待たずに手順 3 へ進む。MINOR・MAJOR を自動では上げない。
- 候補の形（数字 3 つ）を手順 3 のコマンドで確かめる。形が違えばエラーを示し、入力し直しを求める。
- 手順 4 の定型コマンド A（`-Version {候補}`）で、`不明` が 0、`tag` が `無し`、公開済みが 0/4、`GitHub Release` が `無し`、`PR` が `無し` であることを確かめる。満たさないときの扱いは、手順 4 の 3 つの箇条のとおりにする。
- 統合からの再開のとき: この段を行わない（手順 4 は、段 1 の手順 3 の「続け方」で `V` について済んでいる。条件を 1 つでも満たさなければ、別の版の入力を求めずに止まる）。
- 飛ばす: 段 2 の判定が S4・S5・S7 のとき。
- 完了の状態: `V` が確定して開発者に示してあり、そのときの定型コマンド A の出力が手順 4 の条件をすべて満たしている。

### 段 4. 版の表記を更新し、1 つのコミットにする

節「段 4: 版の更新」に従う。

- 手順 1（事前の確認）が不合格なら、何も変えずに止まる。
- 手順 2 で、`Cargo.toml` の版の表記の 3 か所を、Edit の全置換で `V` にそろえる。
- 手順 3（H1〜H4）で、見どころのファイルを書く。定型コマンド D の 4 行がすべて `合格` になるまで、手順 6 を行わない。直すのは 3 回までである。
- 手順 4 の 4 つの確認が、すべて合格の基準を満たすことを確かめる。1 つでも不合格なら、手順 5 で 2 ファイルを元に戻し、不合格の確認を示して止まる。`git restore`・`git checkout --`・`git clean` を使わない。
- 手順 6 で、2 ファイルだけをパスを並べてコミットする。
- 手順 6 の後、見どころのファイルの全文を開発者に示す。承認を求めない。答えを待たずに段 5 へ進む。
- 手元でビルド・テストを行わない。
- 統合からの再開のとき: この段を行わない（確認は段 1 の手順 3 の「続け方」で済んでいる。新しいコミットを作らない）。
- 飛ばす: 段 2 の判定が S4・S5・S7 のとき。
- 完了の状態（統合からの再開でないとき）: `git show --stat --format=%s HEAD` の出力が、件名 `chore(release): v{V}` と 2 ファイルだけである。

### 段 5. 版の更新を PR で main に統合する

節「段 5: main への統合」に従う。

- 手順 1 で、PR に入る変更が 2 ファイルだけであることを確かめてから、作業ブランチを push する。2 ファイルだけでなければ、push せずに止まる。main へは直接 push しない。
- 手順 2・3 で、PR を作り、PR の CI を待たずに squash で統合する。
- 統合の成否は、手順 3 の 2 つ目のコマンドの出力（`MERGED <SHA>`）だけで判定する。そのコマンドを実行できなかったときだけ、手順 3 の代わりの判定（`git log`）を使う。ローカルブランチの削除の警告は、失敗ではない。
- 手順 1〜3 のどれかが失敗したら、リリースタグを作らず、強制 push・履歴の書き換え・ブランチの削除を行わずに止まる（手順 4）。
- 飛ばす: 段 2 の判定が S4・S5・S7 のとき。
- 完了の状態: 手順 3 の出力が `MERGED <SHA>`（代わりの判定では、SHA の 1 行）で、その SHA を `TARGET` とし、手順 5 の定型コマンド C（`-Version {V} -Target {TARGET}`）の 4 行がすべて `合格` である。

### 段 6. リリースタグを作り、タグだけを push する

節「段 6: リリースタグの作成と push」に従う。

- この段のタグの push が、取り消せない公開の入口である。手順 2 と手順 3 が合格するまで、タグを作らない。
- 手順 1 で `TARGET` を決める（段 5 から来たときは段 5 の値、S7 から来たときは手順 1 のコマンド）。見つからなければ止まる。S7 から来て、見どころだけが不合格のときの扱いは、手順 1 のとおりにする。
- 手順 2 で、定型コマンド C の 4 行がすべて `合格` であることを確かめる。不合格なら、タグを作らずに止まる。
- 手順 3 で、同じ名前のタグがリモートにもローカルにも無いことを確かめる。あるときの扱いは、手順 3 の 2 つの箇条のとおりにする。既存のタグを削除しない。付け替えない。
- 手順 4 で注釈付きのタグを作り、手順 5 でタグだけを push する。push が失敗したら、手順 5 のとおりに示して止まる。
- 飛ばす: 段 2 の判定が S4・S5 のとき。
- 完了の状態: `git ls-remote --tags origin refs/tags/v{V}` の出力が空でない。

### 段 7. リリース CI の実行を最後まで追い、公開先ごとの結果を読む

節「段 7: リリース CI の結果の確認」に従う。

- 手順 1 で、タグの名前とタグのコミットの両方が一致する実行を、ツールのタイムアウトを 10 分にして特定し、`RUN` とする。`ATTEMPT` は 1 とする。出力が `run | 無し` なら、完了と報告せずに止まる。S4・S5 から来たときは、手順 1 を行わず、段 2 で取った `RUN` と `ATTEMPT` を使う。
- 手順 2 のコマンドを、ツールのタイムアウトを 10 分にして、出力が `completed` になるまで繰り返す。20 回繰り返しても終わらなければ、「リリース CI が実行中」として止まる。実行中は、完了と報告しない。
- 手順 3 で、定型コマンド B の出力と節「結果表の作り方」の規則 1〜4 から、4 つの公開先（3 クレート・GitHub Release）の `status`・`reason` と、GitHub Release の URL を決める。規則は上から当て、最初に当てはまったものを使う。crates.io の認証の step `Auth crates.io` は 3 クレートで共有する。
- 手順 4 の 3 つの条件（実行の結論が `success`・4 つがすべて `published` か `skipped`・定型コマンド A が公開済み 4/4 で `不明` 0）をすべて満たしたときだけ、完了と判定する。満たしたら段 8 を飛ばして段 9 へ、満たさなければ段 8 へ進む（3 つ目だけ満たさないときの扱いは、手順 4 の最後の段落のとおりにする）。
- 完了の状態: 4 つの公開先の結果表（`status`・`reason`）と実行の URL を開発者に示し、完了か未完了かの判定と、次に行う段の番号を示してある。

### 段 8. 失敗に、判定表に従って対応する（未完了のときだけ）

節「段 8: 失敗への対応」に従う。

- 段 7 の結果表と定型コマンド B の `job` の行を、判定表 F0〜F7（F2・F5 は欠番）に上から当て、最初に当てはまった行に従う。
- 自動で再実行するのは F6 と F7 と、F3 のうち段 8 の「トークンの期限切れの見分け」で期限切れと分かったときだけで、コマンドは段 8 の「失敗した job の再実行」のものだけを使う。`N_AUTO` が 3 になったら、自動の再実行をやめて止まる。F7 の切り分けの再実行は 1 度だけである。
- 再実行のコマンドが終了コード 0 なら、`ATTEMPT` を 1 増やし、段 7 の手順 2・3・4 をやり直す。`N_AUTO` の増やし方は段 8 の「失敗した job の再実行」と「公開前の段の失敗の続き」のとおりにする（開発者の指示による「そのまま再実行」では増やさない）。完了の判定を満たさなければ、もう 1 度この判定表に当てる。
- F0・F1・F3・F4 は自動では再実行せず、判定表の「次の手」のとおりに示して止まる。開発者が「直した」「そのまま再実行」「タグを付け直してよい」と指示したときの続きは、段 8 の「セットアップを直した後の続き」「公開前の段の失敗の続き」のとおりにする。
- タグの付け直しは、開発者の承認が明示されているときだけ、段 8 の「タグの付け直し」の手順 1〜4 で行う。公開済みが 0/4 でなければ、付け直さない。
- 手元から公開しない。GitHub Release を作らない。公開済みのものを取り消さない。上書きしない。
- 止まるときは、「止まり方」の形で報告する。公開より前の段で止めたとき（F1）は、定型コマンド A で 0/4 を確かめたうえで「どの公開先にも公開していない」を含める。
- 飛ばす: 段 7 が完了と判定したとき。
- 完了の状態: 再実行の後に、段 7 の手順 4 の 3 つの条件をすべて満たしている。満たさずに止まるときは、未完了の報告が出ている。

### 段 9. リリースの完了を報告する

節「段 9: 完了の報告」に従う。

- 段 7 の手順 4 の 3 つの条件を満たしているときだけ行う。1 つでも満たさないときは、完了と報告しない。
- 段 9 の報告の形（版・クレートごとの結果・GitHub Release の URL・リリース CI の実行の URL・再実行の回数・手順との食い違い）を、結果表と定型コマンド A・B の出力から埋めて出す。
- リリースの実行は、版の表記と見どころのファイルのほかに文書を変えない。手順の文書（このスキル・`procedure.md`・`.github/release-ci-setup.md`）と、実際の挙動が食い違ったところがあれば、この実行では文書を直さず、報告の「手順との食い違い」に書く。直すのは別の PR で行う。
- 完了の状態: 「リリース完了: v{V}」で始まる報告が、すべての項目を埋めて開発者に出ている。

## まだ実地で確かめていない読み方

次の 3 つは、実地で確かめていない。

1. **再実行の後の読み方**。失敗した job の再実行（段 8 の `gh run rerun {RUN} --failed`）の後に、次の 2 つが成り立つこと。
   - 再実行しなかった job の step の結論が、最新の `gh run view --json jobs`（定型コマンド B の `step` の行）に残る。
   - 前の attempt の `line` が、`--attempt` で読める（定型コマンド B の `line` の行に、前の attempt のものが出る）。
2. **1 回の認証**。job の先頭の `Auth crates.io` で 1 回だけ取ったトークンで、3 クレートをすべて公開できること（crates.io のソースの読みに基づく）。トークンの残り（定型コマンド B の `期限まで`）の数え方も、実際の時刻で確かめていない。
3. **401・403 の分類**。`cargo publish` が 401・403 で失敗したときに、公開の step の `line` が `status=failed reason=auth` になり、判定表 F3 に当たること。

確かめる機会は、1 は初めて段 8 で再実行したリリース、2 と 3 は CI から初めてクレートを公開するリリース（0.0.2）である。そのリリースで確かめ、結果を報告の「手順との食い違い」に書く。

直すときの決まり:

- 食い違いがあれば、その実行では推測で進めずに止まる（実行の約束 8）。その実行では文書を直さない。
- 結果は、別の PR で、この節と `procedure.md`（必要なら `scripts/`）に同時に反映する。確かめた項目は、この節から消す。

## このスキルを直すとき

次のどれかが変わったら、`procedure.md` と `scripts/` を合わせる。

- `release.yml` の job 名・step 名・`status=` の行の形（定型コマンド B と節「結果表の作り方」）。
- `.github/scripts/release/verify-tag.ps1` の検査の条件（定型コマンド C）。
- 公開対象のクレートの追加・削除と公開の順（定型コマンド A のクレートの一覧、集計の `n/4`、節「結果表の作り方」）。
- 版の表記の置き場所（`Cargo.toml` の `[workspace.package]` と `[workspace.dependencies]` の 3 か所。段 4 の手順 1・4 と段 1 の手順 3 の `3`）と、版の更新のコミットに入るファイル（段 4 の 2 ファイル。段 1 の手順 3・段 5 の手順 1 にも出る）。
- 見どころのファイルの置き場所と名前、書き方の決まり（`doc/release-notes/README.md`）、詳しいリリースノートの見出し「動きが変わる変更」（定型コマンド C・D と、段 4 の手順 3）。
- main のブランチ保護・統合方式（squash）、`gh` の `run`・`pr` サブコマンドの出力の形。

リリースの実行中は、`release.yml` とリリースのスクリプトを触る変更を main に入れない。
